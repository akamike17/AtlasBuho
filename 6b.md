# AtlasBuho

## Translator Core + Data Integrity + Mesoamerican UX Architecture

**Project:** AtlasBuho
**Purpose:** Indigenous-language translator
**Primary languages:** Supported Indigenous Languages ↔ Spanish ↔ English
**AI:** Optional / disabled by default
**Priority:** Translation correctness > Data integrity > UX > Performance > AI
**Design objective:** Distinctive Mexican/Mesoamerican visual identity without falsifying cultural attribution
**Engineering objective:** Architecture that is auditable, deterministic, extensible and production-grade

---

# 0. PRODUCT DIRECTIVE

AtlasBuho is first and foremost a **translator**.

It is not an AI chatbot.

It is not an AI language generator.

It is not an automatic linguistic editor.

It is not a social network.

It is not an educational game.

It is not a generic multilingual platform.

Its core function is:

```text
Indigenous Language ↔ Spanish
Indigenous Language ↔ English
```

The first release must be excellent at this one job.

AI is optional.

The application must remain completely functional when:

```text
AI_ENABLED = false
```

The translator must never depend on an external AI provider for basic operation.

---

# 1. PRIORITY ORDER

The implementation priority is mandatory:

```text
1. DATA INTEGRITY
2. TRANSLATION CORRECTNESS
3. DETERMINISTIC BEHAVIOR
4. UX / INTUITIVENESS
5. PERFORMANCE
6. OBSERVABILITY
7. VISUAL IDENTITY
8. OPTIONAL AI
```

Do not reverse this order because visual features are easier or more impressive.

A beautiful translator with unreliable linguistic data is a failure.

A plain translator with perfectly controlled linguistic data is a valid foundation.

The final objective is both.

---

The application must always distinguish:

```text
SOURCE
CANONICAL
TRANSLATION
DERIVED
AI
```

These are not interchangeable.

Conceptually:

```text
SOURCE
   ↓
CANONICAL LINGUISTIC RECORD
   ↓
TRANSLATION ENGINE
   ↓
TRANSLATION RESULT
```

Optional:

```text
TRANSLATION ENGINE
   ↓
AI ASSISTANCE
   ↓
PROPOSAL
```

Never:

```text
AI
 ↓
CANONICAL SOURCE
```

---

# 3. AI IS OPTIONAL

The application must operate normally with:

```text
AI = OFF
```

AI must be an adapter, not the foundation.

Architectural interface:

```text
ITranslationEngine
```

Possible implementations:

```text
DictionaryTranslationEngine
RuleTranslationEngine
CorpusTranslationEngine
HybridTranslationEngine
AITranslationEngine
```

The core application must not directly depend on a specific AI vendor.

Prefer:

```text
Translator
   ↓
ITranslationEngine
```

instead of:

```text
Translator
   ↓
OpenAI/Gemini/etc.
```

The application should be able to run indefinitely without an AI API key.

---

# 4. TRANSLATION ENGINE

The first translation engine should prioritize verified linguistic resources.

Possible hierarchy:

```text
1. Exact verified lexical match
2. Verified phrase match
3. Context-aware verified translation
4. Approved linguistic rule
5. Approved corpus-derived translation
6. Optional AI proposal
7. No verified translation
```

The engine must never silently jump from:

```text
No verified translation
```

to:

```text
Invented translation
```

If no trustworthy translation exists:

```text
No verified translation available.
```

is a valid result.

---

# 5. TRANSLATION MUST BE DETERMINISTIC WHEN USING CANONICAL DATA

Given the same:

```text
source language
target language
input
canonical dataset version
translation engine version
```

the deterministic engine should produce the same result.

Example:

```text
Input:
X

From:
Language A

To:
Spanish

Dataset:
v1.4

Engine:
v1.0
```

must produce reproducible output.

Avoid hidden mutable state.

Avoid random selection.

Avoid non-deterministic ordering.

Avoid arbitrary database ordering.

---

# 6. NO RANDOM TRANSLATION SELECTION

If several translations exist:

```text
A
B
C
```

the system must not randomly choose one.

Define deterministic selection based on documented criteria such as:

```text
verified status
source authority
context
language variant
specificity
dataset version
```

If no deterministic rule can safely select one:

```text
Multiple verified translations available.
```

The UI may display alternatives.

Never silently invent a winner.

---

# 7. LANGUAGE IDENTITY

Each language must have a stable internal identifier.

Do not use display names as database primary keys.

Example:

```text
LanguageId
```

Display:

```text
Náhuatl
```

must not itself be the identity.

The system must support:

```text
LanguageId
OfficialName
Autodenomination
Variant
Family
Group
Status
Source
```

where applicable.

---

# 8. AUTODENOMINATION

The original linguistic form must remain intact.

Never replace it with:

```text
Spanish translation
English translation
administrative name
AI-generated name
```

The UI may display:

```text
Common name
Autodenomination
```

as separate fields.

---

# 9. VARIANTS

Variants must never be merged merely because they appear similar.

The system must represent:

```text
Language
Variant
Dialect
Regional form
Orthographic form
```

according to the actual evidence available.

If the project does not yet have enough evidence to distinguish two forms:

```text
Unknown / unresolved
```

is acceptable.

Do not guess.

---

# 10. SOURCE PRESERVATION

Every canonical linguistic record must retain provenance.

Minimum conceptual metadata:

```text
SourceDocument
SourcePage
SourceOrdinal
SourceVersion
RawDataHash
Origin
CreatedAt
CreatedBy
VerificationStatus
```

Use existing structures where possible.

Do not duplicate existing functionality.

---

# 11. IMMUTABILITY MODEL

Historical linguistic data must never disappear because a new translation or correction was added.

Concept:

```text
Version 1
Version 2
Version 3
```

not:

```text
Version 1
   ↓
overwrite
   ↓
Version 3
```

The system must preserve history.

---

# 12. CANONICAL DATA RULE

Canonical data is authoritative only within its documented source/provenance context.

Do not interpret:

```text
Canonical
```

as:

```text
Universal linguistic truth
```

Instead:

```text
Canonical = verified representation of an identified source/data state.
```

This distinction is essential.

---

# 13. TRANSLATION RECORD

A translation should conceptually contain:

```text
TranslationId
SourceLanguageId
TargetLanguageId
SourceText
TargetText
Context
SourceRecordId
SourceVersion
VerificationStatus
TranslationVersion
CreatedAt
```

Adapt names to the existing domain model.

Do not blindly create duplicate entities.

---

# 14. TRANSLATION DIRECTION

Every translation is directional.

```text
A → B
```

does not automatically imply:

```text
B → A
```

unless there is evidence for the reverse translation.

This prevents one of the most common linguistic data errors:

```text
A → Spanish
```

being incorrectly treated as:

```text
Spanish → A
```

---

# 15. LANGUAGE PAIRS

The product should support:

```text
Indigenous → Spanish
Spanish → Indigenous

Indigenous → English
English → Indigenous
```

Later:

```text
Indigenous A → Indigenous B
```

only when the dataset supports it.

Do not create fake direct mappings by chaining languages invisibly.

---

# 16. PIVOT TRANSLATION

If the engine internally uses Spanish as an intermediate language:

```text
Indigenous A
     ↓
Spanish
     ↓
Indigenous B
```

the system must know that this is a pivot translation.

It must not present it as:

```text
Direct A → B translation
```

unless direct evidence exists.

---

# 17. WORD-LEVEL VS PHRASE-LEVEL TRANSLATION

Support at least:

```text
word
phrase
sentence
```

but do not assume that translating word-by-word always preserves meaning.

Example conceptual pipeline:

```text
Exact phrase
    ↓
Known expression
    ↓
Sentence pattern
    ↓
Lexical fallback
```

The engine should prefer the most specific verified match.

---

# 18. CONTEXT

Translations can depend on context.

The data model should allow:

```text
SourceText
Context
TargetText
```

Examples:

```text
formal
informal
regional
ceremonial
literal
context-specific
```

Only use categories that the actual source data supports.

Do not fabricate context.

---

# 19. UNKNOWN TRANSLATION

The translator must have a first-class unknown state.

Examples:

```text
Translation not available.
```

or:

```text
No verified translation available for this context.
```

This is not an error.

It is a valid linguistic state.

---

# 20. CONFIDENCE

Never confuse AI confidence with linguistic verification.

Bad:

```text
AI confidence = 97%
therefore verified
```

Correct:

```text
ModelConfidence = 0.97
VerificationStatus = Pending
```

These are separate concepts.

---


# 40. DATA INTEGRITY INVARIANTS

The following invariants are mandatory.

### Invariant 1

Source records cannot be silently overwritten.

### Invariant 2

Historical versions remain recoverable.

### Invariant 3

AI cannot directly mutate canonical records.

### Invariant 4

Derived data cannot replace source data.

### Invariant 5

Translation cannot modify linguistic source data.

### Invariant 6

A missing translation remains missing.

### Invariant 7

An unverified translation cannot become verified automatically.

### Invariant 8

Language identity is stable.

### Invariant 9

Source provenance remains attached.

### Invariant 10

The same dataset + deterministic engine + input produces reproducible results.

---

# 41. DATABASE CONSTRAINTS

Use database-level constraints where appropriate.

Examples:

```text
foreign keys
unique constraints
not-null constraints
check constraints
indexes
```

Do not rely exclusively on application validation.

The database should reject structurally invalid states.

---

# 42. APPLICATION VALIDATION

Application validation remains necessary.

The application should reject:

```text
unknown language
unsupported language pair
empty input
invalid request
missing required provenance
invalid translation state
```

Database and application validation should complement each other.

---

# 43. TRANSACTION BOUNDARIES

Operations that create:

```text
translation version
canonical record version
audit record
provenance record
```

must have clearly defined transaction boundaries.

If the operation must be atomic:

```text
BEGIN
...
COMMIT
```

If it fails:

```text
ROLLBACK
```

Real MySQL evidence must be used for claims about real transaction behavior.

---

# 44. NO PARTIAL CANONICAL WRITE

Never allow:

```text
TranslationRecord saved
SourceVersion missing
Audit missing
```

when these records are required to form one atomic operation.

Either the complete operation succeeds or it rolls back.
