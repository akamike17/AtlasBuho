# 2. CUÁNDO SÍ DEBES DETENERTE

Detente únicamente cuando exista una condición que requiera una decisión humana real y que no pueda resolverse razonablemente mediante evidencia técnica.

Ejemplos:

* credencial externa que no existe y que el agente no puede obtener;
* acceso a un servicio externo no disponible;
* requisito contradictorio imposible de resolver técnicamente;
* operación destructiva irreversible fuera del alcance;
* cambio que implique abandonar deliberadamente la arquitectura definida;
* evidencia insuficiente para afirmar que una fase está cerrada.

En esos casos:

1. explica exactamente el bloqueo;
2. indica qué evidencia lo produjo;
3. indica qué dato o decisión falta;
4. NO inventes una solución;
5. NO declares la fase como cerrada.

# 10. PRUEBAS

Toda funcionalidad nueva debe tener evidencia.

Prioridad:

### Nivel 1

Build.

### Nivel 2

Unit tests.

### Nivel 3

Integration tests.

### Nivel 4

Database integration cuando corresponda.

### Nivel 5

Prueba específica del comportamiento crítico.

No aceptar:

```text
"debería funcionar"
```

como evidencia.

Aceptar:

```text
X/X PASS
```

con comando ejecutado.

---

# 11. FALLAS DE TEST

Cuando un test falle:

NO preguntar si debe corregirse.

Investigar automáticamente:

1. leer el test;
2. leer implementación;
3. reproducir;
4. determinar causa;
5. corregir;
6. volver a ejecutar.

Clasificar la causa:

* código incorrecto;
* test incorrecto;
* fixture incorrecto;
* migración incorrecta;
* configuración incorrecta;
* dependencia incorrecta;
* expectativa incompatible con la especificación.

No modificar una expectativa solamente para obtener PASS.

---

# 12. DATOS DE PRUEBA

Los tests de integración deben evitar colisiones.

Preferir:

* IDs únicos;
* nombres únicos;
* GUIDs cuando corresponda;
* cleanup controlado;
* transacciones cuando sean apropiadas.

No depender del orden en que se ejecutan los tests.

Cada test debe poder ejecutarse:

* solo;
* dentro del conjunto completo;
* más de una vez.

---

# 13. SEGURIDAD DE CREDENCIALES

Nunca escribir credenciales reales dentro de:

* código;
* tests;
* migraciones;
* documentación;
* commits;
* logs.

Usar variables de entorno o configuración segura.

Si el repositorio ya tiene un patrón establecido, reutilizarlo.

No crear otro sistema de configuración solamente por preferencia personal.

# 14. GIT

Antes del commit:

```bash
git status
git diff --check
git diff
```

Después:

```bash
git status
git log -1 --oneline
```

El commit debe describir el cambio real.

No hacer commits basura como:

```text
fix
changes
update
test
wip
```

Preferir:

```text
feat: ...
fix: ...
test: ...
refactor: ...
docs: ...
```

---

# 15. PUSH

Una vez que:

* build pasa;
* tests relevantes pasan;
* diff revisado;
* no existen cambios accidentales;
* documentación actualizada cuando corresponda;

hacer push al branch de trabajo.

Verificar que el push realmente ocurrió.

No decir:

```text
push OK
```

sin evidencia del resultado del comando.

---

# 16. NO RECLAMAR CIERRE SIN EVIDENCIA

Una fase solamente puede marcarse:

```text
CLOSED / VERIFIED
```

si existe evidencia de:

* implementación;
* build;
* pruebas;
* migración cuando corresponda;
* integración cuando corresponda;
* revisión del diff;
* Git limpio o cambios esperados;
* commit;
* push.

Si falta evidencia:

```text
IN PROGRESS
```

o:

```text
BLOCKED
```

pero nunca:

```text
VERIFIED
```
